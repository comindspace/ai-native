# eEPC в draw.io

Скилл для работы с диаграммами eEPC (extended Event-driven Process Chain) в формате draw.io.

## Контекст

- **Нотация:** eEPC — расширенная цепочка процессов, управляемых событиями
- **Формат выхода:** `.drawio` XML (совместим с draw.io Desktop, diagrams.net, Confluence draw.io plugin)
- **Правила нотации:** `references/eepc-rules.md`
- **Стили элементов:** `references/drawio-styles.md`

## Когда использовать

- Пользователь просит: "построй eEPC", "нарисуй бизнес-процесс", "сделай диаграмму процесса"
- Пользователь просит: "проверь диаграмму", "валидируй eEPC"
- Пользователь просит: "улучши диаграмму", "исправь ошибки в eEPC", "рефакторинг диаграммы"

## Разрешённые инструменты

- **Read** — чтение .drawio файлов и references
- **Write** — создание/обновление .drawio файлов
- **Grep/Glob** — поиск .drawio файлов в проекте

## Команды

### 1. Генерация eEPC-диаграммы

**Как вызвать:**
```
Построй eEPC-диаграмму для процесса: [описание]
Роли: [список ролей]
Системы: [список ИС]
Документы: [список документов]
Сохранить в: [путь к файлу.drawio]
```

**Что делаю:**

1. **Прочитать references:**
   - Прочитать `references/eepc-rules.md` — все правила нотации
   - Прочитать `references/drawio-styles.md` — все стили и XML-шаблоны

2. **Разобрать описание процесса:**
   - Выделить события (триггеры, результаты) — формулировка: завершённое действие ("Поступила заявка", "Запрос решён")
   - Выделить функции (действия) — формулировка: глагол в инфинитиве ("Определить тему", "Оформить возврат")
   - Определить точки ветвления (XOR/OR/AND) и их ветви
   - Привязать роли, документы, ИС к функциям

3. **Проверить правила:**
   - Процесс начинается и заканчивается событием
   - Нет двух событий подряд (в том числе через точку ветвления: Событие → XOR → События — ошибка; XOR должен идти после функции)
   - Документы/ИС/Роли привязаны только к функциям
   - Роли — без стрелок, документы/ИС — со стрелками
   - У каждого события и функции ровно один вход и один выход по основному потоку
   - Для разделения/слияния — только точки ветвления

4. **Сгенерировать XML:**
   - Использовать точные стили из `references/drawio-styles.md`
   - Все ID уникальные (формат: `elem_1`, `elem_2`, ... для элементов; `edge_1`, `edge_2`, ... для связей; `group_1`, `role_1`, `icon_1` для ролей)
   - Основной поток идёт сверху вниз, центрирован по оси x=480
   - Интервал между элементами основного потока: 35px
   - Роли размещать справа, документы/ИС — слева от функций
   - При ветвлении — ветви расходятся влево/вправо
   - **Горизонтальное выравнивание:** дополнительные элементы (роли, документы, ИС) ОБЯЗАТЕЛЬНО выравнивать по вертикальному центру с функцией, к которой привязаны. Если функция `y=Y, h=70` → документ (h=70) ставить `y=Y`, ИС (h=60) ставить `y=Y+5`, роль (h=80) ставить `y=Y-5`. Иначе orthogonalEdgeStyle создаёт лишний излом
   - **Маршрутизация ветвлений:** стрелки от точки ветвления к ветвям должны выходить с БОКОВ (`exitX=0;exitY=0.5` для левой ветви, `exitX=1;exitY=0.5` для правой), а не снизу. Первый элемент ветви должен быть ≥75px ниже центра точки ветвления. Это даёт чистый L-образный маршрут с одним углом. НЕ использовать `exitX=0.5;exitY=1` для ветвлений — это создаёт двойной излом

5. **Сохранить файл** по указанному пути

**Пример входа:**
```
Построй eEPC для процесса обработки обращения в техподдержку:
1. Пользователь отправляет обращение
2. Специалист первой линии определяет тему (в системе Help Desk, по тикету)
3. Если обращение про выплаты — финансовый специалист проверяет по ERP и оформляет возврат
4. Если обращение про технику — специалист второй линии решает
5. После решения — закрыть тикет и заполнить отчёт о времени
```

### 2. Валидация eEPC-диаграммы

**Как вызвать:**
```
Проверь eEPC-диаграмму: [путь к файлу.drawio]
```

**Что делаю:**

1. **Прочитать references:**
   - `references/eepc-rules.md` — все правила

2. **Прочитать .drawio файл** и разобрать XML

3. **Проверить структуру:**
   - [ ] Процесс начинается событием
   - [ ] Процесс заканчивается событием
   - [ ] Нет двух событий подряд в потоке (в т.ч. через точку ветвления: Событие → XOR → События)
   - [ ] Документы/ИС/Роли привязаны только к функциям (не к событиям, не к точкам ветвления)
   - [ ] Роли соединены без стрелок (`endArrow=none`)
   - [ ] Документы/ИС соединены стрелками (направление соответствует семантике вход/выход)
   - [ ] У каждого события и функции не более одного входа и одного выхода по основному потоку
   - [ ] Для разделения/слияния используются только точки ветвления (XOR/OR/AND)
   - [ ] Точки ветвления парные (разделение + слияние)

4. **Проверить формулировки:**
   - [ ] События сформулированы как завершённое действие
   - [ ] Функции сформулированы как глагол в инфинитиве

5. **Проверить оформление:**
   - [ ] Все основные элементы одной высоты (70px для событий/функций)
   - [ ] Надписи не длиннее 3 строк
   - [ ] Стили соответствуют эталонным из `references/drawio-styles.md`
   - [ ] Шрифт Verdana у всех элементов

6. **Выдать результат:**
   - Ошибки (нарушения правил нотации) — с указанием элемента и правила
   - Предупреждения (стилистические рекомендации)
   - Если ошибок нет — "Диаграмма валидна"

### 3. Рефакторинг eEPC-диаграммы

**Как вызвать:**
```
Улучши eEPC-диаграмму: [путь к файлу.drawio]
Что сделать: [описание изменений или "общая проверка"]
```

**Что делаю:**

1. **Прочитать references** (правила + стили)
2. **Прочитать .drawio файл**
3. **Выполнить валидацию** (команда 2)
4. **Применить исправления:**
   - Исправить ошибки нотации (если возможно автоматически)
   - Стандартизировать стили (привести к эталонным из drawio-styles.md)
   - Выровнять layout (одинаковые интервалы, центрирование)
   - Если пользователь указал конкретные изменения — применить их
5. **Сохранить обновлённый файл**
6. **Выдать diff:** что было изменено и почему

## Ключевые правила нотации (краткая справка)

> Полные правила — в `references/eepc-rules.md`

1. Процесс **начинается и заканчивается событием**
2. Два события подряд **недопустимы** (в т.ч. через точку ветвления — XOR/OR/AND ставится после функции, не после события)
3. **Скелет процесса** = последовательность событий + функций + точек ветвления
4. Документы, ИС, Роли — **только дополнения к функциям**, не могут быть в основном потоке
5. Роли → функция: **без стрелок**. Документы/ИС → функция: **со стрелками** (направление = вход/выход)
6. Ветвление: только через **XOR** (одна ветвь), **OR** (одна или несколько), **AND** (все параллельно)
7. Действия внешних лиц (клиент, посетитель) — это **события**, а не функции

## Связь между процессами

- Последнее событие процесса A = первое событие процесса B (последовательность)
- Детализация функции = отдельный процесс, где первое/последнее события совпадают с событиями до/после этой функции

## Телеметрия

Считай содержательным запуском случай, когда этот skill выбран для выполнения задачи, а не только открыт как справка.

- Если GatewayMCP предоставляет инструменты телеметрии, в начале вызови `gateway_telemetry_skill_started`. Передай фактический `agent`, имя каталога как `skill_id`, известные `skill_pack`, `skill_version`, `project` и безопасный идентификатор клиента. Неизвестные значения оставь пустыми.
- Сохрани `correlation_id` из ответа. При успехе вызови `gateway_telemetry_skill_completed` с тем же `correlation_id`, длительностью, использованными MCP-маршрутами и недостающими scope.
- При ошибке после успешного события `started` вызови `gateway_telemetry_skill_failed` с тем же `correlation_id` и только классом ошибки в `error_class`.
- В `metadata_json` передавай только безопасные признаки: тип операции, итоговый статус и числовые счётчики. Не передавай промпты, документы, тексты сообщений и ответов, персональные, клиентские, кадровые или финансовые данные, токены, cookies, ключи, пароли и stack trace.
- Недоступность телеметрии не должна блокировать основную работу. Не повторяй неуспешную телеметрическую запись больше одного раза.
