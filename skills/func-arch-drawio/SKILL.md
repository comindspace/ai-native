# Функциональная архитектура в draw.io

Скилл для работы с диаграммами функциональной архитектуры в формате draw.io.

## Контекст

- **Нотация:** функциональная архитектура — системы, их функции, роли пользователей, связи и иерархии
- **Формат выхода:** `.drawio` XML (совместим с draw.io Desktop, diagrams.net, Confluence draw.io plugin)
- **Правила нотации:** `references/func-arch-rules.md`
- **Стили элементов:** `references/drawio-styles.md`
- **Детерминированный layout helper:** `scripts/layout_engine.py` — использовать для сложных диаграмм, где нужно минимизировать пересечения стрелок и маршрутизировать ортогональные связи.

## Когда использовать

- Пользователь просит: "нарисуй архитектуру", "покажи функциональную архитектуру", "сделай схему системы"
- Пользователь просит: "нарисуй взаимодействие систем", "покажи какие роли работают с какими системами"
- Пользователь просит: "проверь архитектурную диаграмму", "валидируй схему"
- Пользователь просит: "улучши диаграмму архитектуры", "исправь схему"

## Разрешённые инструменты

- **Read** — чтение .drawio файлов и references
- **Write** — создание/обновление .drawio файлов
- **Grep/Glob** — поиск .drawio файлов в проекте

## Команды

### 1. Генерация диаграммы функциональной архитектуры

**Как вызвать:**
```
Нарисуй функциональную архитектуру для: [описание]
Роли: [список ролей]
Системы: [список систем с функциями]
Связи: [кто с чем взаимодействует]
Сохранить в: [путь к файлу.drawio]
```

**Что делаю:**

1. **Прочитать references:**
   - Прочитать `references/func-arch-rules.md` — все правила нотации
   - Прочитать `references/drawio-styles.md` — все стили и XML-шаблоны

2. **Разобрать описание:**
   - Выделить роли (пользователи, администраторы, внешние участники)
   - Выделить системы и их иерархию (система → подсистема → функция)
   - Определить функциональные блоки внутри каждой системы
   - Определить группировки (организация, контур безопасности, территория)
   - Определить дополнительные элементы (БД, облако, ML-модели, документы)
   - Определить связи: роль→система, система→система, функция→функция
   - Определить типы стрелок (однонаправленные, двунаправленные, разные стили)

3. **Спланировать layout:**
   - Роли — по краям, ближе к «своим» системам
   - Системы-контейнеры — в центре или группами
   - Функции — внутри контейнеров, выровнены в сетку
   - Группировки — на заднем плане, охватывают несколько систем
   - **Группировка не должна охватывать всю диаграмму** — если все элементы внутри одной группировки, она бессмысленна. Либо убрать группировку, либо вынести часть элементов за её пределы, чтобы граница несла смысл (например, роли снаружи, инфраструктура внутри VPN-контура)
   - **Минимизировать пересечения стрелок** — это ключевой критерий. Перебрать варианты расположения, выбрать с минимумом пересечений
   - **Минимизировать изломы стрелок** — выравнивать элементы по вертикали/горизонтали так, чтобы стрелки шли прямо (без поворотов). Для этого exit-точка источника и entry-точка цели должны быть на одной оси
   - **Стрелки от ролей** начинаются от нижнего центра надписи (самый нижний элемент группы), source=`role_X_label`, exitX=0.5, exitY=1
   - Интервалы ≥20px между элементами, ≥40px от верха контейнера до вложенных элементов

4. **Определить цветовую схему:**
   - По умолчанию — **чёрно-белая диаграмма** (без заливок и цветных границ)
   - Цвет вводить **только когда он несёт смысл** и диаграмма достаточно сложна (много элементов, глубокая вложенность), чтобы чёрно-белый вариант был трудночитаем
   - Если цвет используется — он должен быть семантически обоснован (например, зелёный = наша система, голубой = внешняя, оранжевый = deprecated). Нельзя красить один элемент без причины
   - Не использовать `strokeColor`/`fillColor` на единственном элементе — это выглядит случайно

5. **Сгенерировать XML:**
   - Использовать точные стили из `references/drawio-styles.md`
   - Все ID уникальные (формат: `sys_1`, `fn_1`, `role_1`, `grp_1`, `edge_1`, ...)
   - Контейнеры размещаются ДО вложенных в них элементов (draw.io рисует в порядке появления в XML, контейнер должен быть на заднем плане)
   - Группировки размещаются ДО систем, которые в них входят
   - Вложенные элементы НЕ используют `parent="CONTAINER_ID"` — они просто геометрически находятся внутри контейнера (x/y в пределах контейнера). Исключение — элементы внутри `group` (роли)
   - Все функции одной высоты (50 или 60px)
   - Шрифт Verdana для всех надписей
   - `pageWidth`/`pageHeight` подобрать под размер диаграммы

5. **Сохранить файл** по указанному пути

**Пример входа:**
```
Нарисуй функциональную архитектуру для системы видеоконференцсвязи:
Роли: Участник конференции, Администратор конференции
Системы:
- Система видеоконференцсвязи (запись созвонов, формирование приглашений, конспектирование встреч, трансляция экрана)
- Сервис календарей (назначение созвонов)
- Сервис виртуального ассистента (видео-аватар, переход по приглашениям, участие во встрече по задаче)
Связи: Участник → ВКС, ВКС ↔ Ассистент; Администратор → ВКС, Администратор → Календари
```

### 2. Валидация диаграммы функциональной архитектуры

**Как вызвать:**
```
Проверь архитектурную диаграмму: [путь к файлу.drawio]
```

**Что делаю:**

1. **Прочитать references:**
   - `references/func-arch-rules.md` — все правила

2. **Прочитать .drawio файл** и разобрать XML

3. **Проверить структуру:**
   - [ ] Все элементы одного типа имеют одинаковое обозначение (все БД = цилиндр, все модели = шестиугольник и т.д.)
   - [ ] Системы-контейнеры содержат функциональные блоки или пусты (верхнеуровневая схема)
   - [ ] Все функции одной высоты
   - [ ] Роли подключены к системам/функциям стрелками
   - [ ] Нет «висячих» элементов без связей (если только это не осознанный выбор)
   - [ ] Группировки корректно охватывают вложенные системы (геометрически)
   - [ ] Не более 3 типов стрелок на одной диаграмме
   - [ ] «Множественные» объекты: 3 фигуры со смещением, подпись только на переднем

4. **Проверить оформление:**
   - [ ] Надписи не длиннее 2 строк в функциях
   - [ ] Надписи не пересекают границы элементов
   - [ ] Отступы текста от границ ≥10px
   - [ ] Шрифт Verdana у всех элементов
   - [ ] Надписи одного уровня иерархии — одинаковый размер шрифта
   - [ ] Вложенные элементы имеют отступы от границ контейнера ≥20px

5. **Проверить layout:**
   - [ ] Минимум пересечений стрелок
   - [ ] Минимум изломов стрелок (элементы выровнены так, чтобы стрелки шли прямо)
   - [ ] Стрелки от ролей начинаются от надписи (нижний элемент группы), а не от тела/головы
   - [ ] Роли ближе к системам, с которыми взаимодействуют
   - [ ] Элементы не наложены друг на друга (кроме множественных объектов и вложенных)
   - [ ] Контейнеры на заднем плане (раньше в XML), функции — на переднем
   - [ ] Группировка не охватывает всю диаграмму целиком (если да — либо убрать, либо вынести часть элементов наружу)

6. **Проверить цвета:**
   - [ ] Диаграмма либо чёрно-белая, либо цвета семантически обоснованы
   - [ ] Нет единичного элемента с цветной границей/заливкой без причины

6. **Выдать результат:**
   - Ошибки (нарушения правил нотации) — с указанием элемента и правила
   - Предупреждения (стилистические рекомендации)
   - Если ошибок нет — "Диаграмма валидна"

### 3. Рефакторинг диаграммы функциональной архитектуры

**Как вызвать:**
```
Улучши архитектурную диаграмму: [путь к файлу.drawio]
Что сделать: [описание изменений или "общая проверка"]
```

**Что делаю:**

1. **Прочитать references** (правила + стили)
2. **Прочитать .drawio файл**
3. **Выполнить валидацию** (команда 2)
4. **Применить исправления:**
   - Исправить ошибки нотации
   - Стандартизировать стили (привести к эталонным из drawio-styles.md)
   - Улучшить layout (минимизировать пересечения, выровнять элементы)
   - Если пользователь указал конкретные изменения — применить их
5. **Сохранить обновлённый файл**
6. **Выдать diff:** что было изменено и почему

## Ключевые правила нотации (краткая справка)

> Полные правила — в `references/func-arch-rules.md`

1. **Главные элементы** — системы и их функции. Системы могут быть вложены друг в друга (система → подсистема → функция)
2. **Роли** — по краям диаграммы, изображаются как человечек (круг + треугольник + подпись)
3. **Системы** — скруглённые прямоугольники с заголовком сверху, содержат функции
4. **Функции** — прямоугольники одинаковой высоты, текст по центру
5. **Группировки** — объединяют системы логически; пунктирная граница = условная/виртуальная, сплошная = физическая/надсистема. Надпись может быть сверху (`verticalAlign=top`) или снизу (`verticalAlign=bottom`) — выбирать так, чтобы надпись не пересекалась со стрелками и не мешала чтению
6. **Дополнительные элементы** (БД, облако, ML-модель и т.д.) — одинаковое обозначение для всех элементов одного типа
7. **«Множественные» объекты** — 3 перекрывающиеся фигуры, подпись только на передней
8. **Стрелки** — не более 3 типов на одной схеме. Означают взаимодействие, передачу данных или обмен ценностью. Стрелки от ролей начинаются от надписи (нижний элемент группы)
9. **Layout** — минимизация пересечений стрелок, минимизация изломов стрелок (выравнивать элементы чтобы стрелки шли прямо), роли ближе к «своим» системам, минимум когнитивной нагрузки
10. **Группировки** — не должны охватывать всю диаграмму; если все элементы внутри одной группировки, она бессмысленна
11. **Цвета** — по умолчанию чёрно-белая диаграмма. Цвет вводить только когда он несёт смысл и диаграмма достаточно сложна. Нельзя красить один элемент без причины

## Телеметрия

Считай содержательным запуском случай, когда этот skill выбран для выполнения задачи, а не только открыт как справка.

- Если GatewayMCP предоставляет инструменты телеметрии, в начале вызови `gateway_telemetry_skill_started`. Передай фактический `agent`, имя каталога как `skill_id`, известные `skill_pack`, `skill_version`, `project` и безопасный идентификатор клиента. Неизвестные значения оставь пустыми.
- Сохрани `correlation_id` из ответа. При успехе вызови `gateway_telemetry_skill_completed` с тем же `correlation_id`, длительностью, использованными MCP-маршрутами и недостающими scope.
- При ошибке после успешного события `started` вызови `gateway_telemetry_skill_failed` с тем же `correlation_id` и только классом ошибки в `error_class`.
- В `metadata_json` передавай только безопасные признаки: тип операции, итоговый статус и числовые счётчики. Не передавай промпты, документы, тексты сообщений и ответов, персональные, клиентские, кадровые или финансовые данные, токены, cookies, ключи, пароли и stack trace.
- Недоступность телеметрии не должна блокировать основную работу. Не повторяй неуспешную телеметрическую запись больше одного раза.
