# coMind DOCX

Skill для подготовки Word-документов в стиле coMind. Он отделяет универсальные правила документов от КП-специфики.

## Быстрый Маршрут

1. Определи тип документа: КП, отчет, концепция, ТЗ, мемо или другой документ.
2. Для языка и вординга применяй общий `editorial-style` skill.
3. Для любого `.docx` в стиле coMind открой [references/universal-docx-style.md](./references/universal-docx-style.md).
4. Для КП дополнительно открой [references/kp-docx-rules.md](./references/kp-docx-rules.md).
5. Используй шаблоны из `document-templates/references/templates/`.
6. После генерации или правки проверь документ по соответствующему чек-листу и открой через Word COM, если доступен Word.

## Разделение Ответственности

- **Универсальные правила DOCX**: качество Word-верстки, стили, списки, таблицы, отсутствие лишних разрывов и проверка открытия документа.
- **Редакторский стиль**: общий `editorial-style` skill задает правила делового русского языка для всех текстов, включая `.md`, `.docx`, письма, КП и презентационные тезисы.
- **КП-правила**: структура КП, титульный лист, оглавление, страница "О компании coMind", коммерческие таблицы, условия оплаты, допущения и границы работ.
- **Содержательные proposal skills**: `ai-native-proposal`, `sales`, `kp-draft` отвечают за смысл, оценку, коммерческую логику и процесс продаж; этот skill отвечает за финальное `.docx` качество.

## Стандартные Шаблоны

- `document-templates/references/templates/kp-template.docx` — основной КП-шаблон с титулом, оглавлением, примерами `List Bullet` и последней страницей.
- `document-templates/references/templates/kp-template-full-content.docx` — расширенный КП-пример с большим количеством готовых блоков.
- `document-templates/references/templates/kp-blank-template.docx` — пустой КП-шаблон без примеров списков.
- `document-templates/references/templates/last-page-template.docx` — последняя страница "О компании coMind".

## Скрипты

- `scripts/format_kp_docx.py` — постпроцессор и валидатор КП `.docx`. Запускай после генерации или существенной правки клиентского КП:

```bash
python skills/comind-docx/scripts/format_kp_docx.py path/to/proposal.docx
python skills/comind-docx/scripts/format_kp_docx.py path/to/proposal.docx --check
```

Скрипт защищает титульный лист, оглавление и последнюю страницу coMind, форматирует только содержательные таблицы основного тела, проверяет `Heading 1` на последней странице, компактную высоту строк, 11 pt в таблицах, белые внутренние границы темных заголовков и случайно склеенные таблицы.
Дополнительные проверки для строгой сдачи документа:

```bash
python skills/comind-docx/scripts/format_kp_docx.py path/to/document.docx --check --json --allow-missing-about --strict-min-font --disallow-font Aptos --disallow-font Inter
```

Используй строгий режим, если пользователь явно требует отсутствие конкретных шрифтов, общий минимум размера шрифта или документ готовится вне фирменного КП-шаблона. Проверка запрещенных шрифтов смотрит именно font-атрибуты DOCX, поэтому слова вроде `NeuroLiquidInterface` не считаются нарушением.

## Ключевые Правила

- Никогда не собирать документ "с нуля", если есть фирменный `.docx` шаблон: открыть шаблон, сохранить нужные блоки и заменить только рабочий контент.
- Титульный лист, оглавление и последняя брендовая страница являются защищенными зонами шаблона. В них меняй только нужные текстовые значения, не применяй глобальную нормализацию шрифтов, таблиц, отступов или run-форматирования.
- Для основного тела документа используй стили Word (`Title`, `Subtitle`, `Heading 1`, `Heading 2`, `Normal`) вместо прямого задания размера шрифта на run. Прямой размер `11 pt` допустим только для содержательных таблиц, если это требуется правилами.
- В числовых диапазонах используй короткое тире `–`, а не дефис: `2–4 навыка`, `50–100 примеров`, `60–90 минут`. Не меняй дефисы в датах, кодах, идентификаторах, путях и технических значениях.
- Для маркированных списков использовать реальные Word-списки: стиль `List Bullet` и `w:numPr`. Не писать символ `•` как обычный текст, кроме аварийного fallback с явным предупреждением.
- Для нумерованных списков по умолчанию использовать настоящую нумерацию Word. Каждый независимый список должен иметь явный restart через отдельный numbering instance с `w:lvlOverride/w:startOverride=1`; одного нового `numId` без restart-переопределения может быть недостаточно для Word.
- Если Word продолжает склеивать независимые нумерованные списки или документ должен стабильно открываться без ручной правки в Word, допустим fallback с явными номерами обычным текстом. В этом случае не смешивай ручные номера и Word-нумерацию в одном логическом разделе.
- Таблицы сохранять в стиле шаблона: темная шапка с белым текстом, обычные ячейки без заливки и с черным текстом.
- Шапку каждой содержательной таблицы нужно визуально выделять. Минимум: полужирный текст во всех ячейках первой строки; для фирменных документов также сохраняй заливку и контрастный цвет текста из шаблона.
- В анкетных и заполняемых таблицах должны быть видимые границы всех ячеек. Не отдавай форму с невидимой сеткой: пользователю должно быть понятно, где начинается и заканчивается поле для ввода.
- Для клиентских и внутренних документов стиль `Normal` должен быть выровнен по ширине, если пользователь или исходный шаблон явно не требуют другое выравнивание.
- Для анкетных и заполняемых таблиц сначала определи столбцы, куда пользователь будет вносить значения. Делай такие столбцы шире, а в двухколоночных формах отдавай полю ввода почти всю оставшуюся ширину страницы.
- Многостолбцовые таблицы, где большинство столбцов предназначено для пользовательского ввода, нельзя оставлять тесными в книжной ориентации. Разбей их на несколько тематических таблиц или выдели таблицу отдельным разделом с альбомной ориентацией страницы. Если используешь альбомную секцию, разрыв должен стоять перед связанным заголовком или подписью таблицы, а не между заголовком и таблицей.
- Каждая логическая таблица создается отдельной Word-таблицей. Не склеивай две таблицы в одну через повторную строку заголовков; если меняется смысл таблицы, добавь новый заголовок/абзац и отдельную таблицу.
- Между текстом и таблицей всегда должен быть видимый вертикальный интервал. У абзаца перед таблицей задавай `space_after`, у абзаца после таблицы задавай `space_before`; не допускай, чтобы текст визуально прилипал к нижней или верхней границе таблицы.
- Для таблиц ставь `keepNext` на абзац перед таблицей, `w:tblHeader` и `w:cantSplit` на первую строку, `w:cantSplit` на остальные строки. Это снижает риск ситуации, когда на странице остается только строка заголовка таблицы.
- Финальный документ должен открываться без ошибок и не содержать лишних пустых абзацев, разрывов страниц или сломанного `sectPr`.

## Телеметрия

Считай содержательным запуском случай, когда этот skill выбран для выполнения задачи, а не только открыт как справка.

- Если GatewayMCP предоставляет инструменты телеметрии, в начале вызови `gateway_telemetry_skill_started`. Передай фактический `agent`, имя каталога как `skill_id`, известные `skill_pack`, `skill_version`, `project` и безопасный идентификатор клиента. Неизвестные значения оставь пустыми.
- Сохрани `correlation_id` из ответа. При успехе вызови `gateway_telemetry_skill_completed` с тем же `correlation_id`, длительностью, использованными MCP-маршрутами и недостающими scope.
- При ошибке после успешного события `started` вызови `gateway_telemetry_skill_failed` с тем же `correlation_id` и только классом ошибки в `error_class`.
- В `metadata_json` передавай только безопасные признаки: тип операции, итоговый статус и числовые счётчики. Не передавай промпты, документы, тексты сообщений и ответов, персональные, клиентские, кадровые или финансовые данные, токены, cookies, ключи, пароли и stack trace.
- Недоступность телеметрии не должна блокировать основную работу. Не повторяй неуспешную телеметрическую запись больше одного раза.
