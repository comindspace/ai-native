# Definition of Ready (DoR)

## Чек-лист готовности задачи

Задача готова к взятию в спринт если выполнены все пункты:

### Обязательные критерии

| Критерий | Ответственный | Проверяет |
|----------|---------------|-----------|
| **Описание понятно** — из текста ясно что нужно сделать | PM | Tech Lead |
| **Acceptance Criteria** — критерии приёмки (минимум 1) | PM + Tech Lead | QA |
| **Wiki links** — ссылки на артефакты в Yonote (или явное N/A) | PM | Tech Lead + QA |
| **Project/Queue и Epic** — указаны (Epic обязателен для не‑Epic задач) | PM | Tech Lead |
| **Story Points** — оценка (1, 2, 3, 5, 8) | Команда (planning poker) | PM |
| **Приоритет** — Critical / High / Medium / Low | PM / Product Owner | — |

### Желательные критерии

| Критерий | Ответственный | Проверяет |
|----------|---------------|-----------|
| **Зависимости** — блокирующие задачи | Tech Lead | PM |
| **Исполнитель** — назначен | PM / Tech Lead | — |
| **Мокапы/дизайн** — приложены (UI-задачи) | Designer / PM | Developer |
| **API-контракт** — определён (интеграции) | Tech Lead | Backend Dev |

## DoR по типам задач (что обязательно, чтобы “не гадать”)

### Story / Feature (пользовательская ценность)

Обязательно:
- **Понятное описание** (что меняем в продукте и зачем)
- **Acceptance Criteria** (обычно 2–5 пунктов; если есть ошибки/валидации — они тоже в AC)
- **Wiki links**: `Index`, `Requirements`, `Test Plan` + `UJM` (или `N/A`), `ADR` (или `N/A`)
- **UX/Дизайн**: ссылка на макеты или явное `N/A`
- **Story Points + Priority**

### Technical Task (инфраструктура/рефакторинг/внутренние работы)

Обязательно:
- **Цель и границы** (что улучшаем / что не делаем)
- **Критерий успеха** (метрика, команда, чек-лист — что будет означать “готово”)
- **Риски/миграции** (если затрагивает данные/контракты/производительность)
- **Wiki links**: `Index`, `Test Plan` (или `N/A`), `ADR` (или `N/A`), `Requirements` (или `N/A`)
- **Story Points + Priority**

### Bug

Обязательно:
- **Шаги воспроизведения** + **окружение** (staging/prod, версия, URL)
- **Ожидаемый vs фактический результат**
- **Логи/скрин/видео** (или явное “нет”)
- **AC фикса**: как проверить, что баг исправлен + минимальная регрессия
- **Priority/Severity** + бизнес-эффект (1 строка)

### Release / Deploy / Hotfix

Обязательно:
- **Состав релиза** (milestone/список задач) и “что не входит”
- **QA gate пройден** (что именно прогнали)
- **Release notes + Runbook/rollback** актуальны
- **Коммуникации** (кто/когда/куда уведомляет)

### RACI матрица

```
R = Responsible (делает)
A = Accountable (отвечает за результат)
C = Consulted (консультирует)
I = Informed (информируется)

                    PM    Tech Lead   Dev    QA    Designer
─────────────────────────────────────────────────────────────
Описание            R,A      C         I      I       C
Acceptance Criteria R,A      R         C      C       -
Story Points        A        C         R      -       -
Приоритет           R,A      C         I      I       -
Зависимости         I        R,A       C      -       -
Исполнитель         R,A      R         -      -       -
Мокапы              C        -         I      -       R,A
API-контракт        I        R,A       C      -       -
```

## Автоматическая проверка

Claude может проверить задачи в Tracker на соответствие DoR:

```
Проверь задачи в очереди [KEY]
```

### Что проверяется

| Поле | Проверка | Обязательно |
|------|----------|-------------|
| Description | Длина > 50 символов | Да |
| Acceptance Criteria | Есть хотя бы 1 пункт | Да |
| Wiki links | Есть блок `Wiki:` и минимум `Index/Requirements/Test Plan` (UJM/ADR или `N/A`) | Да |
| Project/Queue | Указан проект/очередь | Да |
| Epic | Указан Epic (или `N/A` для Epic-задачи) | Да |
| Story Points | Заполнено | Да |
| Priority | Заполнено | Да |
| Assignee | Заполнено | Нет |
| Links | Есть зависимости или "нет" | Нет |

## DoR для задач, которые отдаём в Cursor Cloud (минимальный “Cursor-ready brief”)

Чтобы Cursor мог начать работу без “догадок”, в задаче должны быть:
- **Goal** (1–2 предложения)
- **Scope / Out of scope**
- **Acceptance Criteria** (чеклист)
- **Links** (Wiki/дизайн/API/референсы)
- **Constraints** (стек, запреты, SLO/перфоманс если нужно)
- **Test plan** (как проверить)

Рекомендуемая вставка в описание задачи:

```text
Cursor-ready brief:
- Goal:
- Scope:
- Out of scope:
- AC:
- Constraints:
- Test plan:
```

### Формат блока Wiki (копипаста)

В описание Epic/Story/Task добавляйте:

```text
Wiki:
- Index: <link to 00-Index>
- Requirements: <link>
- UJM: <link or N/A>
- ADR: <link or N/A>
- Test Plan: <link or N/A>
```

### Пример отчёта

```
DoR Check для очереди SHOPNAME
══════════════════════════════

✅ Соответствуют DoR: 12 задач
⚠️ Требуют доработки: 3 задачи

SHOPNAME-15: "Интеграция с 1С"
  ❌ Нет Acceptance Criteria
  ❌ Story Points не указаны

SHOPNAME-18: "Дашборд аналитики"
  ❌ Описание слишком короткое (23 символа)

SHOPNAME-21: "Фильтры каталога"
  ⚠️ Нет исполнителя (желательно)

Рекомендация: Доработать 3 задачи перед sprint planning
```

## Примеры

### Хорошая задача (DoR пройден)

```markdown
**Summary:** Добавить блок "Похожие товары" на страницу товара

**Description:**
На странице товара (/product/{id}) добавить блок с рекомендациями
похожих товаров. Блок располагается под описанием товара.
Показывать 4-6 товаров в ряд (desktop) или 2 (mobile).
Данные получать из API /api/recommendations/{product_id}.

**Acceptance Criteria:**
- [ ] Блок отображается под описанием товара
- [ ] Показывается 4-6 товаров (desktop), 2 (mobile)
- [ ] Каждый товар кликабелен, ведёт на страницу товара
- [ ] При ошибке API блок скрывается (не показывать ошибку)
- [ ] Время загрузки блока < 500ms

**Story Points:** 5
**Priority:** High
**Assignee:** @developer
**Links:** Зависит от SHOPNAME-10 (API рекомендаций)
```

### Плохая задача (DoR не пройден)

```markdown
**Summary:** Сделать рекомендации

**Description:**
Добавить рекомендации на сайт

**Acceptance Criteria:** —
**Story Points:** —
**Priority:** —
```

Проблемы:
- Описание не информативно
- Нет acceptance criteria
- Нет оценки
- Нет приоритета
